# Evaluation: `discovery_agentic_replacement_recommendation.md` vs. the actual repo

**Purpose:** feasibility/correctness check of Opus's recommendation against the repo, not a design or refactor. Every claim below was checked against source (`skeleton_store.py`, `delta_engine.py`, `confidence_engine.py`, `agents/series_agent.py`, `services/series_check_engine.py`, `discovery_engine.py`, `services/auto_discovery.py`, `services/discovery_telemetry.py`, `models.py`) as it exists today. No code was changed to produce this document.

**Bottom line up front:** the recommendation is unusually well-grounded — nearly every specific code citation (line numbers, thresholds, field names, docstring quotes) checks out exactly. The mechanism/policy split it proposes is real and matches the map. But it contains **one overclaimed correctness guarantee that is false as written** (§2.3's "confidence engine and gate agree by construction"), **one underspecified core change** (`confidence_engine`'s new `unverified` grade needs a complete decision table, not a point-fix), and **one scope ambiguity** in how `delta_engine`'s `numbering_gaps` is meant to be read. None of these invalidate the plan; all three must be closed before Phase 0 is "done."

---

## 1. Which parts are compatible with the repo?

Verified accurate, no code changes needed to rely on them:

- **The insertion point.** `services/series_check_engine.py:311-314` is exactly the single `ThreadPoolExecutor(max_workers=1)` + `executor.submit(series_agent.run_series_check, db, series_id, update_progress, False, telemetry, discovery_cache)` call the recommendation cites. An engine-selector swap here is a real, minimal seam — confirmed, not aspirational.
- **The persistence-purity claim.** `agents/series_agent.py` contains exactly one `db.commit()` (line 959), preceded only by `series.has_new_books = found` / `series.last_checked = today` (lines 957-958). There is no other `db.add`/`db.delete`/`db.merge` anywhere in that file. The claim "discovery never writes Book rows" is not an approximation — it's literally true today, so an agentic engine dropped into the same seam inherits this for free as long as it doesn't add new writes.
- **The return-schema superset approach.** `_build_added_book_entry` (`agents/series_agent.py:296-321`) emits exactly the field set the recommendation's §2.8 JSON shows (`title`, `author`, `series_name`, `book_number`, `source_url`, `provider`, `publication_date`, `expected_date`, `status_hint`, `asin_or_id`, `is_missing`, `status`, `canonical_metadata{...}`). Matching this shape field-for-field, as recommended, is sufficient for compatibility with `series_check_engine.py`'s persistence code — confirmed by reading what it actually reads (`.get("title")`, `.get("canonical_metadata")`, etc. per map §2.8, and independently confirmed against the real function above).
- **`delta_engine`/`confidence_engine` as pure, repeatedly-callable functions.** Both are stateless pure functions of their arguments (`compute_series_delta(series_id, skeleton_entries, provider_candidates, ...)`, `compute_confidence(series_id, skeleton_entries, provider_candidates, delta, ...)`) with no memoization or hidden state. Calling them once per agent turn with a growing `provider_candidates` list (§2.2) requires **zero code changes** to either module — this is a genuinely free, low-risk adoption, not just a plausible-sounding one.
- **The threshold/constant citations.** `WEB_SEARCH_LOOKAHEAD_BOOKS = 10`, `MAX_MISSING_VOLUME_LOOKAHEAD_QUERIES = 6`, `SERIES_CHECK_MAX_ROUNDS = 3`, `SERIES_CHECK_HARD_TIMEOUT_SECONDS = 300`, `RECONCILIATION_SERIES_COMPLETENESS_THRESHOLD = 0.8`, `RECONCILIATION_METADATA_COMPLETENESS_THRESHOLD = 0.5`, `RECONCILIATION_DISAGREEMENT_RATIO_THRESHOLD = 0.2`, `FALLBACK_SERIES_COMPLETENESS_THRESHOLD = 0.5`, `FALLBACK_CONFIDENCE_THRESHOLD = 0.35` — all confirmed exact.
- **The `all_providers_failed` semantics claim.** `discovery_engine.py:3576-3580`'s comment literally says what the recommendation attributes to it: failure means "every call raised," not "filtering left zero candidates." Directly reusable as an invariant for an agent's own error semantics.
- **The auto-discovery asymmetry.** `services/auto_discovery.is_series_eligible_for_auto_discovery` is confirmed to be a real, separate, conservative gate; `routers/series.py:223`'s manual Check Now endpoint calls `run_series_check_job_full` directly with no eligibility check anywhere in that file. The "manual = override, auto = conservative" claim is accurate.
- **No existing `Provider` protocol.** Confirmed — there is no base class/registry in `discovery_engine.py`; every fetcher is a bare function. §3.2's "introduce a `WebSearchProvider` protocol" proposal doesn't conflict with or duplicate anything that already exists.
- **No existing telemetry counters for agent turns/tool calls.** `services/discovery_telemetry.py` only has `record_brave_call` and `record_llm_call`. The three proposed additions (`record_tool_call`, `record_agent_turn`, `record_gate_outcome`) are genuinely additive — pass names are confirmed to be open strings (map's claim, independently verified: no enum constrains them), so adding new pass labels is safe.

## 2. Which parts violate invariants or integration points?

Nothing in the recommendation **as designed** violates a hard invariant — its own §1.3 restates the map's invariants correctly and its §4.1/§4.2 integration design (engine selector only, persistence unchanged, skeleton write deferred to post-persistence) is specifically constructed to avoid violating them. The risk here is not "the plan breaks an invariant" but "the plan's *justification* for one safety claim is wrong" (see §5 below) and "one proposed change quietly redefines what 'safe to call repeatedly' means for `skeleton_store`" (see §3).

One integration-point subtlety the recommendation doesn't fully resolve: **`backfill_all_skeletons()` runs in its own standalone session on every boot** (`services/skeleton_store.py:84-99`, `SessionLocal()` + its own `commit()`), while a Check Now job's proposed post-persistence skeleton write would run inside `series_check_engine.py`'s existing request-scoped session. §0.1 and §4.2 correctly identify that both paths must converge on the same merge rule, but neither section addresses the case where boot-time backfill and an in-flight Check Now job's skeleton write could race on the same `SeriesSkeleton` row (boot backfill is a one-time startup sweep today, so this is a narrow window, but it stops being narow the moment skeleton writes become routine — worth a row-level lock or upsert-with-retry note in Phase 0, not left implicit).

## 3. Which parts misunderstand the existing scaffold?

Nothing rises to "misunderstanding" — the two "blocking defects" in §0 are both real and both traced to the correct lines. But one framing is imprecise enough to cause a real implementation mistake:

**`delta_engine.numbering_gaps` is a re-corroboration signal, not a "new volume might exist" signal — and §2.4's "gap probe" framing risks conflating the two.** Today, `skeleton_entries` (Phase 1) contains only *owned* books (`skeleton_store._book_to_skeleton_entry` is built exclusively from `active_books`). So `compute_series_delta`'s `numbering_gaps = skeleton_numbers - found_numbers` (`delta_engine.py:159`) can only ever answer "which *already-owned* book numbers did this round's candidates fail to re-surface" — never "book 14 probably exists and I don't own it," because an unowned book 14 is not in `skeleton_numbers` in the first place. The recommendation's own §2.2 table describes this correctly in isolation ("skeleton has it, this run's candidates didn't confirm it"), and §2.4's rule (2) does correctly route the *actual* new-volume-gap logic through the new `expected_total` field instead — so the plan is internally consistent once read end-to-end. The risk is purely that §2.4's rule (1), "interior gaps the skeleton knows about," reads at a glance like it means "gaps in the numbering," which is the natural (and wrong) assumption for whoever implements Phase 1 of the agent without reading §2.1-2.2 closely first. Worth stating explicitly, not just implying via careful phrasing: **`numbering_gaps` becomes a genuine "new volume" signal only after the skeleton is `source_class: "discovered"`-populated by at least one prior agent run; on a series's first agentic pass, it is not that signal, and `expected_total`-derived arithmetic is the only source of it.**

## 4. Which parts require changes to `skeleton_store`, `delta_engine`, or `confidence_engine`?

- **`skeleton_store.py` — requires a real change, and it's two distinct changes, not one.** The recommendation's §0.1 fix ("merge keyed on `book_number`... library-sourced entries rebuilt from ground truth, non-library entries preserved") and §4.2's "agent returns `skeleton_updates`/`probes`; `series_check_engine.py` applies them after persistence" describe **two different write paths** that both land in `skeleton_store.py`:
  1. `backfill_skeleton_for_series` needs to change from "assign `entries` wholesale" (`skeleton_store.py:79`, `skeleton.skeleton_json = entries`) to a merge against whatever non-library entries already exist on that row.
  2. A **new function** is needed for applying agent-returned `skeleton_updates`/`probes` post-persistence — nothing today does this, and it isn't a variant of `backfill_skeleton_for_series` (that function's whole shape is "rebuild from `Book` rows," it takes no candidate/finding input at all).
  The recommendation gestures at both but presents them as one "fix," which will read as smaller than it is. It should be scoped as two functions with two call sites (`main.py:30` boot call; `series_check_engine.py` post-persistence call), sharing one merge rule.
  Also unaddressed: **what happens to a `source_class: "discovered"` entry when the corresponding number never gets confirmed and the library never owns it** — does it expire, per the `ttl_days` on `probes` (§2.1), or persist indefinitely as `status: "confirmed"` on nothing but agent say-so? §2.7's "unresolved ≠ fabricated" principle implies discovered-and-confirmed entries should carry real corroboration, but the merge rule itself needs an explicit "what if a discovered entry never gets owned" retention/expiry policy, which §0.1 doesn't specify.
- **`delta_engine.py` — no change required for the recommendation's core proposal** (per §2, it's a pure function already compatible with per-turn calling). The only "change" implied is conceptual/documentation: making explicit that `numbering_gaps` is corroboration-only until the skeleton has discovered entries (see §3 above). Code-wise, this module can ship as-is into Phase 1.
- **`confidence_engine.py` — requires a real, non-trivial change**, larger than the recommendation's framing suggests. Adding `unverified` means:
  - A fifth grade added to `_title_confidence`'s return values (today: `zero`/`high`/`medium`/`low` only, confirmed at `confidence_engine.py:97-123`).
  - `_LEVEL_RANK` (line 42, today `{"zero": 0, "low": 1, "medium": 2, "high": 3}`) needs `unverified` placed somewhere in the order, and it isn't obviously between `low` and `medium` for every use — `_provider_confidence`'s `max(levels, key=...)` (line 90) and `_title_confidence`'s own internal logic don't currently need rank-ordering for `unverified`, but `_overall_confidence` (lines 206-221) does, and its current logic is a **hand-written total order over exactly 4 grades**, not a generic max/min over a rank table. The recommendation specifies exactly one new rule ("`unverified` on title alone, everything else `high`/`medium` → `medium`") — it does **not** specify the other combinations that become newly reachable: `unverified` + one `low` elsewhere; `unverified` + one `zero` elsewhere (probably still `zero`, but that's an assumption, not a stated rule); `unverified` alone with everything else `high` (is that `high` or capped at `medium`, given title is *unverified* not *confirmed*?). This is a real design gap, not an implementation detail — `_overall_confidence`'s "round down toward caution" principle needs a complete statement before this ships, not a single worked example.

## 5. Which parts are safe to adopt?

- The mechanism/policy split (§1.1) and its two lists — this is the load-bearing architectural claim of the whole document, and it matches the map's own §4.1/§4.2 split almost 1:1 (independently verified by re-reading `discovery_engine.py`'s `_fuse_and_score_candidates`, `_filter_and_merge`, `services/identity.py`'s three collapse-pass call sites, and `agents/series_agent.py`'s `belongs_to_series` gate). Safe to treat as the governing principle.
- The insertion point, engine-selector design, and "nothing else in the round loop changes on day one" claim (§4.1) — verified against the actual round-loop code, including the stop condition (`series_check_engine.py:769-772`, confirmed single-signal "zero new books persisted," matching the map and the recommendation's citation of it) and the fresh-DB-read-per-round behavior (`agents/series_agent.py:351-358`, confirmed `highest_owned_book_number` is recomputed from `active_series_books` every call, not cached).
- Deferring skeleton writes to post-persistence, single-writer discipline (§4.2) — this is a genuinely good design decision and is safe to adopt as a principle now, independent of when the merge-rule code actually ships.
- The phased rollout (shadow → canary → primary → loop-ownership-last) — consistent with the existing per-job telemetry/cache lifecycle and doesn't require any of it to change shape.
- Reusing `_author_matches`' hard-reject semantics and `precheck_for_new_volumes`' zero-cost gate as non-negotiable pre-agent checks — both confirmed to exist exactly as described and safe to keep as-is.

## 6. Which parts are risky or incorrect?

**Incorrect as stated:** §2.3's claim that "the confidence engine and the acceptance gate agree by construction" on author-mismatch `zero`. This does not hold. `confidence_engine._series_alignment_confidence` (lines 146-179) and `discovery_engine._author_matches` (lines 849-859) are **two independently-implemented author-matching algorithms**, not one function called from two places:

- `_author_matches`: for each split target-author name, checks whether **all of its normalized tokens appear as substrings** within **any single** candidate-author string (`all(token in candidate_norm for token in target_tokens)`).
- `_series_alignment_confidence`: requires **exact token-set equality** for `high`, or a surname match plus a bespoke initials-abbreviation heuristic (`_given_names_are_initials_variant`) for `medium`; anything else is `zero`.

These produce different verdicts on real cases — e.g., a candidate author string containing extra tokens the target doesn't have (a co-author byline, a "with Jane Doe" credit, a middle name `_author_matches` tolerates via substring containment but `_series_alignment_confidence`'s exact-set-equality branch does not) can pass `_author_matches` while landing on `medium` or even structurally missing `_series_alignment_confidence`'s narrow surname-plus-initials carve-out and reading `zero`. There is no shared code, shared test, or runtime coupling enforcing agreement — "by construction" overstates what's actually true, which is "by current coincidence for the cases exercised so far." If Phase 0's escalation policy (§2.3's table) is built on the assumption that `confidence_engine`'s `zero` is a strict subset of `_author_matches`'s reject set, that assumption needs a real test (feed the eval-set fixtures from §5 Phase 0 through both functions and diff), not an assertion. This is easy to fix (either make `_series_alignment_confidence` call `_author_matches` directly, or add the eval case), but as written it is a false guarantee load-bearing enough to gate an escalation policy on.

**Risky (underspecified, not wrong):** the `unverified` grade's incomplete decision table, per §4 above — shipping §0.2 "as specified" (one worked example) rather than as a complete rule will produce undefined behavior for real combinations the first time a genuinely ambiguous candidate appears (e.g., `unverified` title + `zero` alignment — almost certainly still `zero` given `_overall_confidence`'s "any zero wins outright" first rule, so this specific case is actually fine by the *existing* rule structure — but `unverified` + `low` elsewhere is genuinely new and unaddressed).

**Risky (market/pricing claims, out of scope for a repo evaluation but worth flagging as unverified):** §3's Tavily/Exa/SerpAPI pricing table and the "Bing retired 11 August 2025" claim are not repo-grounded and weren't checked here — they're vendor facts, not code facts, and should be re-verified against current pricing pages before Phase 0 procurement, independent of this evaluation's scope.

**Not risky, but worth flagging as a scope-creep watch item:** §2.1's `probes` schema (`probe_kind`, `outcome`, `ttl_days`) and §2.8's full `agent` sub-object in the return schema are reasonable, but they are *new* schema surface with no existing analog anywhere in the repo (confirmed: no `ttl_days`, `probe_kind`, or similar concept exists today). That's fine — Phase 1 shadow mode is exactly where new schema should get proven out — but it means Phase 0's "no agent code" framing slightly understates the work: designing this schema correctly is itself a design task that should happen before Phase 1, not be improvised during it.

## 7. What constraints must be preserved if we move to agentic?

All seven invariants in the recommendation's §1.3 were independently re-verified against source rather than taken on the map's word, and all seven hold exactly as stated:

1. URL-keyed, never index-keyed, downstream of any LLM call — structurally true of `_structure_with_verdict_cache` today; must hold for any agent tool-call response handling.
2. Original list order preserved on reassembly — same.
3. A cached rejection is not final (`bypass_cached_rejection` escape hatch) — confirmed real, confirmed narrow/deliberate.
4. "Rejected" ≠ "never checked" (`None` vs. `CACHE_MISS` sentinel, `discovery_cache.py:42`) — confirmed.
5. Confidence tags survive re-merges (`_filter_and_merge:1780`-adjacent logic) — confirmed as a named regression fix (Jonathan Hunt), not a hypothetical.
6. `all_providers_failed` means zero usable data, not zero surviving candidates — confirmed exact at `discovery_engine.py:3576-3580`.
7. Profile isolation is absolute — confirmed via `agents/series_agent.py`'s `profile_id`-scoped queries throughout `run_series_check`.

Two additional constraints this evaluation surfaced that aren't explicit in either document and should be added to the list before Phase 0:

8. **`SeriesSkeleton` writes must be single-writer per row per commit boundary.** Once skeleton writes move from "boot-only, one process, one commit" to "boot backfill *and* per-job post-persistence merge," a race between the two paths becomes possible for the first time. Needs an explicit rule (row lock, optimistic version check, or simply: boot backfill skips any series with a `SeriesSkeleton.schema_version` indicating agent-authored content and only continues to fully own series with library-only skeletons).
9. **Any new "agree by construction" claim between two independently-implemented functions (e.g., `confidence_engine` vs. `_author_matches`) must be backed by a shared eval fixture, not an assertion** — this is the general form of the §6 finding, and it will recur as more of `confidence_engine`/`delta_engine` gets treated as load-bearing rather than shadow-diagnostic.

## 8. What is the minimal safe surface area for agentic integration?

Narrower than the recommendation's own Phase 0 list, if the goal is strictly "smallest slice that can start producing evidence without any load-bearing correctness claims yet unverified":

**Ship with zero risk, today, no code changes:**
- Call `delta_engine.compute_series_delta` / `confidence_engine.compute_confidence` per agent turn instead of once — free, pure functions, no change needed.
- Build the eval-fixture set (Jonathan Hunt, Safehold, Starship's Mage, universe-tie-in, compilation-of-owned-titles) — pure data work, touches nothing.
- Add the `WebSearchProvider` protocol and a fixture-backed provider — additive, no existing call site needs to change yet.
- Add the three telemetry counters — additive, confirmed no naming collision.

**Ship in Phase 0, but scope as two changes with an explicit eval gate, not one "fix":**
- `skeleton_store.py`: (a) merge-on-rebuild for `backfill_skeleton_for_series`, with an explicit retention/expiry rule for `discovered`-only entries that never get owned; (b) a new post-persistence apply-findings function, called from `series_check_engine.py`, with a stated single-writer rule against (a)'s boot-time path.
- `confidence_engine.py`: the `unverified` grade, specified as a **complete** replacement decision table for `_overall_confidence` (all reachable combinations), not one worked example — and gated on a fixture test proving `_series_alignment_confidence`'s `zero` is actually a subset of `_author_matches`'s reject set before any escalation policy is allowed to assume it.

**Do not touch yet (matches both documents' consensus, independently confirmed safe to defer):**
- `_fuse_and_score_candidates`, `_filter_and_merge`, `_finalize_candidates`, `finalize_discovery_output`.
- `services/identity.py` and the three identity-collapse passes in `series_check_engine.py`.
- `belongs_to_series` / `_is_known_candidate` in `agents/series_agent.py`.
- `precheck_for_new_volumes`.
- The round loop's stop condition and `SERIES_CHECK_MAX_ROUNDS` — explicitly last in both documents' sequencing, and this evaluation found no reason to disagree.
- Provider vendor selection (Tavily/Exa/etc.) — defer until the fixture-based eval set exists to actually compare providers against, per the recommendation's own §3.4 "eval-only: SerpAPI" logic, which is sound.

**One gate to add before Phase 1 shadow-mode is declared meaningful, beyond what either document states:** the eval suite (§5 Phase 0, item 1 in the recommendation) must include at least one fixture that exercises `confidence_engine._series_alignment_confidence` against a candidate `_author_matches` would accept via substring/co-author containment but the exact-set-equality branch would not — i.e., a regression test for the §6 finding, not just the five named historical regressions. Without it, "agreement rate on already-accepted books ≥ 95%" (Phase 1's gate) could pass while this specific disagreement class remains silently present, because none of the five named fixtures happen to exercise it.
